# Callboard feature backlog

Implement these features in the addon. Each item covers rule authoring, runtime behavior, and the checks that define completion.
Please run / create applicable tests after completing each task. Update the TODO.
Keep the readme in sync with the code.

## 1. Call and relay payloads in guards

- [x] Let a stage definition optionally declare typed payload fields for its Calls and relays. In guard expressions such as `payload.action == "confirm"`, the `payload.` prefix identifies an incoming field. Bare keys continue to refer to the Blackboard.
- [x] Support string and Boolean equality, numeric comparisons, and field presence checks. A missing or incompatible field makes a value comparison fail, including inequality. Provide a separate presence check for rules that intentionally handle missing fields.
- [x] Use the event payload in `requires`, `forbids`, and `cancel_if`. Recheck queued runs against their own payload when they start and use the active run's payload at cancellation checkpoints. Preserve payload fields when forwarding relays and keep engine bookkeeping out of the authored field namespace.
- [x] Show fields from the selected trigger in the rule inspector. Validate field names and operand types where a schema is available, and list payload references separately from Blackboard dependencies.
- **Done when** one Call routes different payloads to different rules, with coverage for missing fields, relays, queued runs, and cancellation after a wait. **Complete:** `addons/callboard/tests/unit.gd` covers routing, incompatible/missing values, relays, per-run queued payloads, and cancellation after a queued wait; the editor inspector exposes and validates trigger schemas.

## 2. Numeric Blackboard updates

- [x] Add an `add_var(key, delta)` core verb. Read the current value when the step executes and write the result through the Blackboard. Allow negative deltas and preserve the declared numeric type.
- [x] Register the target as both a read and a write. Offer numeric keys in the step editor and flag invalid operands, including fractional deltas for integer keys.
- **Done when** repeated Calls update the same counter, a later step sees the new value, and saved counters continue from their restored value. **Complete:** Unit coverage checks repeated updates, subsequent reads, restored saved values, integer/float type preservation, negative deltas, target type validation, and fractional integer rejection. Editor coverage checks numeric-key filtering and per-key delta precision. Item 6 should combine this counter pattern with a saved Boolean for each individual gift, so completed-house rules stay simple while duplicate deliveries and restored per-gift visuals remain precise.

## 3. Contextual interactions

- [x] Add prompt text, an optional icon, and priority to interactable triggers. Include an eligibility hook that receives the interacting actor and can query the host game's current state.
- [x] Provide a resolver that selects one eligible trigger for an actor from overlapping candidates. Use a deterministic tie-break, update the selected prompt when availability changes, and dispatch only to the selected trigger. Let any input action or UI subscribe to the selected prompt and invoke the same interaction API.
- [x] Pass an interaction context to the handler and let the handler produce the outcome and payload for Callboard. Projects supply inventory, item consumption, and interaction policy through this integration point.
- **Done when** overlapping triggers yield one prompt and one dispatch, eligibility can change while the actor stays in range, and accepted and rejected attempts can drive different rules. **Complete:** `InteractionResolver` picks by priority, distance, then node path, publishes prompt/selection changes, and dispatches through the same API. Runtime coverage checks dynamic eligibility, deterministic ties, accepted and rejected Calls, and context payloads.
- **Item 6 integration:** During the managed lifecycle work below, the resolver and trigger eligibility path must ignore triggers whose owning Stage is dormant or deactivated. A neighbor yard in a streamed scene window must never provide a prompt or accept an interaction until its Stage is active.

## 5. External Blackboard writers

- [x] Add an editor-facing registration mechanism for external Blackboard writers. Let addon components and gameplay scripts declare which keys they own, including keys passed to latch helpers and per-gift saved keys owned by a `GiftTarget`. Keep existing `external_vars` declarations valid.
- [x] Use the same declarations in editor analysis and runtime validation. Treat declared external writes as producers, flag undeclared or incompatible keys, and keep warnings for keys with no known producer. Route actual writes through the typed Blackboard API and expose the writer source in the live debugger when available.
- [x] Document how scene components publish continuous or per-frame state as Blackboard values or discrete Calls. Give scripts a supported way to declare their outputs so a stage author can see where a guard's inputs come from, including how a `GiftTarget` declares and writes its saved delivered flag through the typed Blackboard API.
- **Done when** a scene component's declared output can feed a guard without a false warning, an undeclared key is diagnosed, and an external latch appears as a writer. **Complete:** `BlackboardWriter` scene nodes expose typed declarations collected by Stage analysis and runtime setup; scripts can declare outputs with `register_external_writer()`. Validation diagnoses missing keys and type mismatches while preserving legacy `external_vars`. Typed writes track source labels in the live Blackboard, including `fire_relay_once()` latches. README/API docs show continuous values, discrete Calls, and per-gift saved Boolean declarations. Unit and editor coverage verifies guard producer detection, type diagnostics, component publishing, and latch attribution.

## 6. Stage persistence and activation

- [x] Provide a reusable state store keyed by stable stage instance ID. Store each stage's saved Blackboard values and one-shot rule latches together. Support restoring that state before stage initialization and preserve the existing dictionary injection path for current callers.
- [x] Add an explicit shared Blackboard scope backed by the same store. Validate types and propagate changes to loaded stages that declare the shared key. Keep local values, stage-saved values, and shared values selectable in the Blackboard editor.
- [x] Provide an opt-in managed lifecycle for streamed stages. Load and restore a stage while dormant, activate it once on entry, and cancel pending work and ignore incoming Calls on deactivation. Keep the existing lifecycle behavior for stages that have not opted in. Make the owning Stage's active/dormant state available to `TriggerArea` eligibility and `InteractionResolver`, so interactions from dormant neighbor stages are filtered out as well as their Calls.
- [x] Add declarative restoration bindings from saved or shared values to supported node properties such as visibility, transforms, and light state. Support a saved Boolean binding that snaps a `Node3D`'s transform to a referenced `Marker3D`, plus an optional resolved pose on an `AnimationPlayer` by animation name. Apply bindings after state loads and before activation. Validate node paths, marker/animation references, and value types in the editor, and retain the script hook for custom restoration. Cover changes such as Buster moving to a doghouse and sleeping (House 1), a squirrel appearing in a planter (House 2), the owl posing asleep in earmuffs (House 6), and a garage door restoring halfway open (House 5). The goal is to restore common house/yard changes without custom `_restore_state()` code per scene.
- [x] Support multi-gift stages by pairing a saved Boolean per gift with a saved numeric delivery counter updated through `add_var`. Use each gift's saved flag to reject duplicate deliveries through its `GiftTarget` eligibility hook and restore the corresponding individual visual (such as a bedroom window silhouette) after reload. Keep the counter for simple completion rules and aggregate progress in Houses 2, 4, and 5; for example, House 5 can use `delivered_bricks`, `delivered_skateboard`, and `delivered_robot` alongside `gifts_delivered`.
- **Done when** two instances of the same stage scene retain independent state and latches through unload and reload, exchange shared values without activation-time copying, and restore their visuals while dormant without dispatching Calls or starting rule loops. Coverage should also prove a saved flag can snap a prop to its `Marker3D` and pose its animation, a dormant neighbor exposes no interaction prompt, and a multi-gift stage prevents duplicate delivery while restoring each gift's visual and continuing its saved counter. **Complete:** `StageStateStore` injects per-instance saved values and latches before initialization, coordinates typed shared keys across loaded boards, and loads/unloads Stage scenes by stable ID. `StageDefinition.managed_lifecycle` keeps opted-in Stages dormant until activation; dormant Calls and interactions are filtered. `StageRestorationBinding` restores visibility, saved transforms, Marker3D snaps, and optional AnimationPlayer poses before activation while retaining `_restore_state()` for custom behavior. Blackboard scope now includes Local, Saved, and Shared. The demo uses the store, and tests cover independent same-scene instances, shared propagation and type conflicts, dormant interaction filtering, saved latches, two distinct gift flags and visuals, counter continuation, and editor binding validation.
