I reviewed Callboard’s addon at [`bbe04e1`](https://github.com/chrisnathan1983/Callboard/commit/bbe04e1a8cc08d1a193daeef049ed510b7debb23), including the rule engine, Blackboard and persistence, staging verbs, graph editor, live debugger, and packaging. I left the demo out of the review. The addon unit and editor smoke assertions passed on Godot **4.6.3**, and the packaged ZIP imported into a blank project. The editor smoke run reported leaked objects and rendering resources at exit. The repo’s CI targets **4.7.2**, which I didn’t run locally. No source changes were made.

My recommendation is to fix wait handling and shared-state writes first. The most valuable additions after that are **immediate relay emission, typed values from the payload or Blackboard, and a cancellable wait with a timeout**. Together, those would let designers author substantially more behavior directly on the board.

## Highest-priority runtime findings

| Priority | Finding | What I would change |
| --- | --- | --- |
| High | **A waiting rule can resume for the wrong animation or stall after playback stops.** I started a rule waiting for one clip, played a different clip on the same player, and saw the rule run its next step when the second clip finished. Stopping playback left the rule active. A looping clip also kept a Restart pending. The public `interruptible()` helper failed on a two-argument signal. [Playback verbs](https://github.com/chrisnathan1983/Callboard/blob/bbe04e1/addons/callboard/core/staging_verbs.gd#L29) · [Wait handling](https://github.com/chrisnathan1983/Callboard/blob/bbe04e1/addons/callboard/core/rule_engine.gd#L137) | Give each run ownership of its waits. Match completion to the requested playback and define what happens on interruption, target removal, timeout, Restart, and Stage deactivation. |
| High | **A shared Blackboard write can overwrite a newer write.** In a probe, Stage A wrote `1` and its change listener triggered a write of `2` from Stage B. B observed `2`, then `1`, and the store ended at `1`. The original write broadcasts after local listeners run, and the store writes the older value again during that broadcast. [Blackboard write order](https://github.com/chrisnathan1983/Callboard/blob/bbe04e1/addons/callboard/core/blackboard.gd#L47) · [Store broadcast](https://github.com/chrisnathan1983/Callboard/blob/bbe04e1/addons/callboard/core/stage_state_store.gd#L86) | Have the store commit each shared write once and deliver notifications in commit order, including writes triggered by listeners. |
| High | **`fire_relay_once()` can fire repeatedly when its latch write is rejected.** With conflicting shared key types across two Stages, both calls returned `true` and emitted the relay while the latch stayed `false`. [Relay latch](https://github.com/chrisnathan1983/Callboard/blob/bbe04e1/addons/callboard/core/stage.gd#L221) | Return a write result and emit only after the latch is successfully committed. |
| High | **Invalid graphs can still run through `Stage.fire()`.** Compilation errors block `activate()`, but an unmanaged Stage accepts direct Calls, and the compiler keeps executable rules alongside inert placeholders for invalid steps. I reproduced a side effect on a Stage with graph errors. The API documents this distinction, so tightening it needs compatibility consideration. [Activation and dispatch](https://github.com/chrisnathan1983/Callboard/blob/bbe04e1/addons/callboard/core/stage.gd#L144) · [Graph compilation](https://github.com/chrisnathan1983/Callboard/blob/bbe04e1/addons/callboard/core/stage_definition.gd#L178) | Apply the same initialization and graph-validity checks at every public dispatch entry point. Give diagnostics enough detail to identify the blocked Call and rule. |
| High | **A feedback loop can monopolize a frame.** Two queued rules that call each other through the public `fire()` API executed 1,000 times inside one call in a bounded probe. Public dispatch resets relay depth, and queue draining has no work budget. [Dispatch and queue draining](https://github.com/chrisnathan1983/Callboard/blob/bbe04e1/addons/callboard/core/rule_engine.gd#L55) | Carry event ancestry across nested dispatch, bound queue size and per-frame work, and show the event chain when a limit is reached. |

## Validation, authoring, and integration gaps

- **One-shot rules can be consumed before they do anything.** An already-true `Cancel If` gate still consumed the latch and emitted `rule_fired` before the first step. Check initial cancellation before recording the start. Keep the existing start-latch behavior for runs that actually start, and consider an explicit completion-latch policy for sequences that must be retryable after interruption. [Run startup](https://github.com/chrisnathan1983/Callboard/blob/bbe04e1/addons/callboard/core/rule_engine.gd#L98)
- **The editor can approve a graph that behaves differently at runtime.** `set_var` passed validation when writing a string to a Boolean key, and runtime discarded the write. An undeclared payload schema produced an “incompatible literal or operator” warning for a comparison the runtime accepted. Integer equality is approximate after casting to `float`, so `1000001 == 1000000` passed in a Blackboard guard. Use one set of type rules across compilation, validation, and evaluation, and compare integers exactly. [Validator](https://github.com/chrisnathan1983/Callboard/blob/bbe04e1/addons/callboard/core/rule_validator.gd#L38) · [Guard evaluation](https://github.com/chrisnathan1983/Callboard/blob/bbe04e1/addons/callboard/core/guard_expression.gd#L51)
- **“Shared” scope is easy to misconfigure in the board.** New variables receive generated storage keys. Changing their scope to Shared leaves those keys in place, so two independently authored Stages can show the same variable name and never share a value. The API explains the storage-key requirement, but the panel exposes only the scope. Also, `StageStateStore.attach()` accepts an already initialized Stage even though its Blackboard and engine have already captured their backing dictionaries. Expose a shared-key picker or a project-level schema, and enforce attachment before initialization. [Blackboard panel](https://github.com/chrisnathan1983/Callboard/blob/bbe04e1/addons/callboard/editor/blackboard_panel.gd#L100) · [Store attachment](https://github.com/chrisnathan1983/Callboard/blob/bbe04e1/addons/callboard/core/stage_state_store.gd#L24)
- **Opening or editing a board can execute project code.** Analysis adds the preview scene to the editor’s scene tree, runs Stage build hooks, and evaluates step argument expressions against the verb factory. For a project with side-effectful `@tool` setup, a routine graph edit can run that setup again. Separate static checks from scene-backed validation and document which hooks must be safe to run in the editor. [Graph analysis](https://github.com/chrisnathan1983/Callboard/blob/bbe04e1/addons/callboard/model/rule_graph_reader.gd#L32) · [Expression evaluation](https://github.com/chrisnathan1983/Callboard/blob/bbe04e1/addons/callboard/core/stage_definition.gd#L206)
- **`TriggerArea` takes over the installing project’s collision setup.** It overwrites the scene’s collision layer and mask in `_ready()` and additionally requires exact `Player` or `Companion` group names for enter triggers. Honor scene-configured layers and masks, expose an optional actor filter, and add an exit Call. [Trigger setup](https://github.com/chrisnathan1983/Callboard/blob/bbe04e1/addons/callboard/core/trigger_area.gd#L26)
- **Overlapping `flash` effects can leave a multi-surface mesh tinted.** I reproduced this with two rules flashing the same mesh. Each effect writes a single cached base color entry per mesh, so a second flash can capture an in-progress tint as the base. Track base colors per material or surface and verify that overlapping effects restore each original color. [Material and tint handling](https://github.com/chrisnathan1983/Callboard/blob/bbe04e1/addons/callboard/core/staging_verbs.gd#L205)
- **The installed ZIP registers a test panel whose scripts are absent.** The plugin always adds **Callboard Tests**, while packaging intentionally excludes its addon tests. The editor runner also grades suites by exit code alone, so it can show PASS despite engine errors. Hide the developer panel when the suites are unavailable, and add an addon-only CI fixture that exercises a clean install, debug and release exports, and repeated teardown. [Plugin registration](https://github.com/chrisnathan1983/Callboard/blob/bbe04e1/addons/callboard/plugin.gd#L21) · [Runner result handling](https://github.com/chrisnathan1983/Callboard/blob/bbe04e1/addons/callboard/editor/test_runner_panel.gd#L196) · [Packaging](https://github.com/chrisnathan1983/Callboard/blob/bbe04e1/.github/scripts/package_addon.py#L41)

## Verbs and features I would add

| Order | Addition | What it unlocks |
| --- | --- | --- |
| 1 | **`emit_relay` with payload forwarding and optional field mapping** | Signal another rule at a chosen point in a sequence. Today the built-ins offer a completion relay and `repeat_emit`, leaving a straightforward mid-sequence relay to custom code. |
| 2 | **Typed step inputs from `payload` and the Blackboard** | Let one rule set a flag, add a supplied amount, display text, or forward a host request using the current Call’s data. Built-in arguments are currently evaluated when the Stage builds, even though custom step callbacks can read the runtime payload. |
| 3 | **`wait_for_call` and `wait_until` with timeout and cancellation** | Wait for acknowledgment, animation-driven gameplay, or a state change. Expose success, timeout, and interruption to the rule so authors can build recovery paths. |
| 4 | **`toggle_var` and `reset_var`** | Cover switches and repeatable puzzles with declared, typed writes. `reset_var` should restore the declared default and explain its effect on Saved and Shared values. |
| 5 | **`snap_to_marker`, `set_interaction_enabled`, and `restart_particles`** | Cover common scene staging directly. Marker snapping already exists in restoration, but a live rule has to approximate it with movement and rotation or use a custom verb. Disabling an interaction should also update the prompt. |

Three editor features would make those additions easier to use:

- **Explain why a rule didn’t run.** Show the failed guard and observed value, latch state, or re-entry decision. Add a typed payload form to the live Call tester, which currently fires Calls with an empty payload. [Live Call dispatch](https://github.com/chrisnathan1983/Callboard/blob/bbe04e1/addons/callboard/editor/callboard.gd#L695) · [Engine trace](https://github.com/chrisnathan1983/Callboard/blob/bbe04e1/addons/callboard/core/rule_engine.gd#L200)
- **Make execution order visible and editable.** Same-Call rules are evaluated in authored order, and a synchronous write from an earlier rule can change whether a later rule qualifies. Surface that order in the editor, and add a fallback or first-match option for mutually exclusive routes. [Dispatch order](https://github.com/chrisnathan1983/Callboard/blob/bbe04e1/addons/callboard/core/rule_engine.gd#L58)
- **Make resolved state authorable from the board.** Add typed restoration controls for visibility, marker transforms, and standalone animation poses. The current board’s fallback text editor can turn a manually authored `Transform3D` default into a `String` when edited, and animation poses are coupled to marker restoration. [Default editor](https://github.com/chrisnathan1983/Callboard/blob/bbe04e1/addons/callboard/editor/blackboard_panel.gd#L140) · [Restoration binding](https://github.com/chrisnathan1983/Callboard/blob/bbe04e1/addons/callboard/core/stage_restoration_binding.gd#L33)

I’d keep inventory, quests, dialogue, and navigation behind the existing custom-verb and `gameplay_event` hooks. The missing piece there is an optional **request-and-acknowledgment contract** so a graph can react to what the game actually did. That would give Callboard more reach across projects while keeping game-specific decisions with the host.
